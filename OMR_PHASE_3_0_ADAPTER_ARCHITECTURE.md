## 1. Почему четыре раздельных адаптера, а не один?

В архитектуре OMR выделены четыре специализированных интеграционных направления:

```text
                               ┌────────────────────────────────┐
                               │     CANONICAL AIL CORE GATE    │
                               │  (Агностичен к типу протокола) │
                               └────────────────┬───────────────┘
                                                │
         ┌───────────────────────┬──────────────┴───────────────┬────────────────────────┐
         │                       │                              │                        │
         ▼                       ▼                              ▼                        ▼
 ┌───────────────┐       ┌───────────────┐              ┌───────────────┐        ┌───────────────┐
 │   TRACK A:    │       │   TRACK B:    │              │   TRACK C:    │        │   TRACK D:    │
 │ TypeScript /  │       │   REST API    │              │  MCP Server   │        │ External Tool │
 │  JS Core SDK  │       │    Gateway    │              │    Adapter    │        │    Adapter    │
 └───────┬───────┘       └───────┬───────┘              └───────┬───────┘        └───────┬───────┘
         │                       │                              │                        │
         ▼                       ▼                              ▼                        ▼
  Внутрипроцессные        Сетевые удалённые              LLM-агенты через         Сторонние CAD /
   агенты, тесты,          сервисы, веб-UI,              стандарт Model           симуляторы оригами
   локальный SOL          облачные платформы            Context Protocol         (Orihime, FOLD, etc.)
```

### Сравнительный анализ четырёх интеграционных осей
| Параметр | Track A: TypeScript SDK | Track B: REST API Gateway | Track C: MCP Adapter | Track D: External Tool Adapter |
| :--- | :--- | :--- | :--- | :--- |
| **Среда выполнения** | Внутрипроцессный (In-process memory) | Сетевой сервис (HTTP/JSON over TCP) | JSON-RPC через stdio / SSE | Сетевой / файловый мост к сторонним программам |
| **Накладные расходы** | Нулевые (прямые вызовы функций, `0 ms`) | Сериализация, парсинг, TCP handshake | JSON-RPC фрейминг, контекст модели | Конвертация форматов, запуск внешнего процесса |
| **Целевой потребитель** | Разработчики TS, локальные тесты, SOL | Web-интерфейсы, SaaS, микросервисы | Интеллектуальные агенты (Claude, Gemini, GPT) | Физические симуляторы, CAD-пакеты оригами |
| **Уровень доверия** | Высокий (код выполняется в том же рантайме) | Средний (аутентификация по API-ключам) | Низкий (LLM-агент генерирует промпты/запросы) | **Критически низкий (`UNTRUSTED CLAIM`)** |
| **Направление потока** | Агент $\to$ OMR Core | Агент $\to$ OMR Core | LLM $\to$ OMR Core | **OMR Core $\to$ Внешний инструмент $\to$ L7** |

Объединение этих потоков в один монолитный адаптер разрушит модульность OMR: SDK требует минимальных накладных расходов и строгой статической типизации без сериализации, тогда как External Tool Adapter требует изолированных песочниц и конвертеров в форматы сторонних симуляторов.

## 2. Track A: TypeScript / JavaScript Core SDK

### 2.1 Ответственность
- Предоставление разработчикам и локальным агентам (работающим в среде Node.js / Browser) строго типизированного, внутрипроцессного программного интерфейса к AIL.
- Прямое взаимодействие с каноническим ядром без сетевых задержек и без лишней JSON-сериализации.
- Обеспечение синхронного и асинхронного выполнения цепочек с полной поддержкой TypeScript `"strict": true`.

### 2.2 Входные и выходные данные
- **Вход:** Строго типизированный объект `AilSubmitRequestInput` (типизированный `GeometryState`, `LineNormalParams`, `movingVertexIds`).
- **Выход:** `AilExecutionResult` с вложенным `resultingState: GeometryState`, `verdict: VerificationVerdict` и `witness: ReflectionWitness`.

### 2.3 Ошибки и ограничения
- **Ошибки:** Выбрасывает типизированные исключения `AilValidationError`, `L2EngineError`, `L7VerificationError`.
- **Ограничения:** Доступен только в среде JavaScript / TypeScript (Node.js $\ge 20$). Не обеспечивает изоляцию памяти от сбоев внутри процесса.
- **Уровень доверия:** Доверенный программный слой приложения.

## 3. Track B: REST API Gateway

### 3.1 Ответственность
- Обеспечение удаленного сетевого доступа к математическому ядру OMR для веб-приложений, облачных агентов и сторонних микросервисов по протоколу HTTP/HTTPS.
- Аутентификация клиентов по Bearer токенам / API-ключам, контроль rate-limits и логирование аудита.
- Преобразование HTTP JSON payload в канонические структуры AIL и обратная сериализация.

### 3.2 Спецификация эндпоинтов REST
1. `GET /api/v3/capabilities`
   - Возвращает каталог возможностей OMR (`GET_CAPABILITIES`).
2. `POST /api/v3/operations/reflect`
   - Принимает `AilRequest`, выполняет операцию `REFLECTION_ACROSS_LINE` и возвращает `AilResponse`.
3. `POST /api/v3/verify/result`
   - Принимает пару `(claim, request)` и возвращает изолированный вердикт `L7` (`verifyResult`).
4. `POST /api/v3/verify/process`
   - Принимает массив `trace` и `trustedRequests`, возвращает процессный вердикт `L7` (`verifyProcess`).
5. `GET /api/v3/trace/:operationId`
   - Возвращает историческую запись из журнала `TRACE`.

### 3.3 Ошибки и ограничения
- **Ошибки:** Стандартные HTTP статус-коды: `400 Bad Request` (ошибка валидации), `404 Not Found`, `422 Unprocessable Entity` (математический сбой / `UNDETERMINED`), `429 Too Many Requests`, `500 Internal Error`.
- **Ограничения:** Накладные расходы на сетевой транспорт и парсинг JSON; необходимость управления таймаутами при больших геометрических сетках.
- **Уровень доверия:** Недоверенный периметр сети; требует обязательной строгой схемы валидации входного JSON.

## 4. Track C: Model Context Protocol (MCP) Adapter

### 4.1 Ответственность
- Интеграция OMR в экосистему интеллектуальных агентов по открытому стандарту **Model Context Protocol (MCP)** от Anthropic, поддержанному сообществом разработчиков AI-агентов.
- Экспорт математических возможностей ядра в виде стандартизированных MCP Tools и MCP Resources.
- Предоставление LLM-агенту контекста ошибок верификации в форме, понятной для последующего самоисправления (Self-Correction Loop).

### 4.2 Проектируемый набор MCP Tools

#### 1. `omr_get_capabilities`
- **Описание:** Возвращает список поддерживаемых геометрических операций, доступных верификаторов и известных ограничений ядра.
- **Параметры:** Нет.

#### 2. `omr_submit_operation`
- **Описание:** Выполняет геометрическую операцию над состоянием листа бумаги и автоматически запускает независимую верификацию.
- **Параметры:**
  ```json
  {
    "operation": "REFLECTION_ACROSS_LINE",
    "sourceState": { "$ref": "#/definitions/GeometryState" },
    "parameters": {
      "line": { "nx": 1.0, "ny": -1.0, "c": 0.0 },
      "movingVertexIds": ["V1"],
      "fixedVertexIds": ["V0", "V2", "V3"]
    },
    "enableVerification": true
  }
  ```
- **Возврат:** `AilResponse` с четким указанием статуса: `VERIFIED`, `VIOLATED` или `INDETERMINATE`.

#### 3. `omr_verify_result`
- **Описание:** Вызывает только независимый верификатор `L7` для перепроверки внешнего или ранее полученного результата.
- **Параметры:** `claim` (`sourceState`, `resultingState`, `witness`) и `request` (`OperationRequest`).

#### 4. `omr_get_trace`
- **Описание:** Возвращает запись журнала `TRACE` по идентификатору шага для аудита многошаговой траектории.

### 4.3 Уровень доверия и правила MCP
- LLM-агент признается **недоверенным генератором гипотез**.
- MCP-адаптер никогда не доверяет промпту агента, если агент утверждает, что сгиб выполнен успешно. Адаптер возвращает в контекст модели объективный вердикт `L7`.

## 5. Track D: External Tool Adapter (Мост к сторонним программам оригами)

### 5.1 Ответственность и фундаментальное отличие
В отличие от адаптеров A, B и C, которые принимают запросы **ОТ** агентов к OMR, **External Tool Adapter** передает задачи **ИЗ** OMR во **внешние программы** (например, в свободные симуляторы оригами, движки сгибания жестких панелей или CAD-пакеты):

```text
  [OMR AIL Gateway]
          │
          ▼
  [External Tool Adapter]
          │
          ├── 1. Трансляция GeometryState -> Внешний формат (.FOLD, TreeMaker, OBJ)
          ├── 2. Запуск внешнего решателя / симулятора (Sandboxed Execution)
          ├── 3. Чтение рассчитанной сторонней геометрии
          └── 4. Присвоение метки: UNTRUSTED_EXTERNAL_CLAIM
          │
          ▼
  [L7 Independent Verifier] ──► Строгая проверка аксиом и изометрии (Zero-Trust)
```

### 5.2 Ключевое правило: `External Tools Are Never Trusted Verifiers`
Ни одна внешняя программа (симулятор оригами, геометрический решатель, физический движок) **не имеет права объявить операцию доказанной**:
1. Все координаты, рассчитанные сторонним инструментом, упаковываются в структуру `VerificationClaim` как недоверенное предположение.
2. Внутренний верификатор `L7` выполняет полную независимую перепроверку: сохранение длин ребер, неподвижность фиксированных вершин, аксиомы отражения, инверсию ориентации граней.
3. Если сторонний симулятор вернул искаженные координаты — вердикт `L7` будет строго `'FAIL'`, независимо от того, какие статусы выставила сторонняя программа.

### 5.3 Ошибки и ограничения
- **Ошибки:** `EXTERNAL_TOOL_NOT_FOUND`, `EXTERNAL_TOOL_TIMEOUT`, `CONVERSION_SYNTAX_ERROR`, `UNTRUSTED_EXTERNAL_CLAIM_REJECTED`.
- **Ограничения:** Необходимость поддержки сторонних файловых спецификаций (например, `.fold` JSON format); изоляция процессов операционной системы.
- **Уровень доверия:** **Нулевой (Zero-Trust External Input).**
