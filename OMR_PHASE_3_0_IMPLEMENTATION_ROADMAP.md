## 2. Детальная спецификация этапов (`Stage 0 — Stage 7`)

### Stage 0 — Architecture Approval (Утверждение архитектуры AIL)
- **Цель:** Формальное рассмотрение и утверждение владельцем проекта пяти проектных документов Phase 3.0 (`OMR_PHASE_3_0_*`).
- **Зависимости:** Завершение Phase 2.6 (Аудит документации и согласованности).
- **Необходимые файлы:** Документы спецификации Phase 3.0 в корне репозитория.
- **Критерии готовности:** Официальное решение владельца проекта в `OMR_ARCHITECTURE_DECISION_RECORD.md` (`ADR-012: ACCEPTED`).
- **Тесты:** Не применимо (документационный этап).
- **Риски:** Преждевременный старт кодирования до согласования статусной модели и JSON-схем.

---

### Stage 1 — Canonical Interface Contract (Канонический контракт интерфейса)
- **Цель:** Создание изолированного модуля канонических типов и JSON-валидаторов AIL в кодовой базе без изменения существующих файлов `src/core/*`.
- **Зависимости:** Успешное завершение Stage 0; отсутствие регрессий в `tests/contract02.test.ts`.
- **Проектируемые файлы:**
  - `src/ail/types.ts` — канонические типы запросов `AilRequest`, ответов `AilResponse`, статусов `ServiceStatus`;
  - `src/ail/validation.ts` — валидаторы допустимости чисел, уникальности идентификаторов и координатных конвертов;
  - `src/ail/capabilities.ts` — реестр `CapabilityRegistry`.
- **Критерии готовности:**
  - Все типы строго типизированы (`strict: true`), без использования `any`.
  - Модуль `src/ail/*` импортирует только чистые типы из `src/core/types.ts` и фабрику `createOperationRequest`.
- **Тестовая матрица:**
  - Unit-тесты валидации корректных и некорректных структур `AilRequest`.
  - Тесты на отсечение `NaN`, `Infinity`, дублирующихся `VertexId` и вырожденных нормалей.
- **Риски:** Случайное внесение изменений в существующие файлы `src/core/types.ts` или `l7IndependentVerifier.ts`.

---

### Stage 2 — In-Process TypeScript SDK (Внутрипроцессный SDK)
- **Цель:** Реализация высокопроизводительного, строго типизированного клиентского класса `OmrClient` для локального взаимодействия с ядром.
- **Зависимости:** Stage 1 (типы и валидация).
- **Проектируемые файлы:**
  - `src/ail/sdk/OmrClient.ts` — публичный фасадный класс с методами:
    - `getCapabilities(): Promise<AilCapabilitiesResponse>`
    - `submitOperation(input: AilSubmitInput): Promise<AilResponse>`
    - `verifyClaim(claim: VerificationClaim, request: OperationRequest): Promise<VerificationVerdict>`
    - `getTraceEntry(operationId: string): Promise<TraceEntry | null>`
- **Критерии готовности:**
  - Вызов `submitOperation` детерминированно выполняет `L2` и автоматически вызывает `L7`.
  - Накладные расходы на вызов не превышают `1 мс` на типовом полигоне из 50 вершин.
- **Тестовая матрица:**
  - Сквозные тесты `tests/ail/sdk.test.ts` (положительные сценарии отражения, обработка `L2EngineError`, ложные `FAIL` и `UNDETERMINED`).
  - Проверка иммутабельности возвращаемых структур.
- **Риски:** Игнорирование вердикта `L7` при формировании итогового ответа SDK.

---

### Stage 3 — Local Agent Integration (Интеграция локальных скриптов агентов)
- **Цель:** Разработка типовых адаптеров и примеров для вызова OMR из скриптов агентов на базе Google GenAI SDK (`@google/genai`) и Anthropic SDK в Node.js.
- **Зависимости:** Stage 2 (TypeScript SDK).
- **Проектируемые файлы:**
  - `examples/agents/gemini_local_planner.ts` — пример трансляции промпта пользователя в `AilRequest` через Gemini Function Calling.
  - `examples/agents/claude_local_auditor.ts` — пример аудита многошаговой трассы через Claude.
- **Критерии готовности:**
  - Локальный агент способен успешно запросить `capabilities`, сгенерировать корректный `AilRequest`, выполнить операцию и проанализировать вердикт `L7`.
- **Тестовая матрица:**
  - Интеграционные тесты с mock-агентами (проверка устойчивости к галлюцинациям в координатах и неверным `VertexId`).
- **Риски:** Агент генерирует координаты с модулем $> 10^{6}$, вызывая дефект `D-1` (должно парироваться понятным сообщением об ограничении).

---

### Stage 4 — Model Context Protocol (MCP Server)
- **Цель:** Реализация стандартного MCP-сервера для прямого подключения OMR к Desktop- и CLI-агентам (Claude Desktop, Cursor, Gemini Code Assist, локальные MCP-клиенты).
- **Зависимости:** Stage 1, Stage 2.
- **Проектируемые файлы:**
  - `src/ail/mcp/server.ts` — точка входа MCP-сервера поверх `@modelcontextprotocol/sdk`;
  - `src/ail/mcp/tools.ts` — реализация инструментов:
    - `omr_get_capabilities`
    - `omr_submit_operation`
    - `omr_verify_result`
    - `omr_get_trace`
- **Критерии готовности:**
  - MCP-сервер успешно инициализируется по протоколу stdio / SSE.
  - Схемы входных параметров инструментов автоматически генерируются из JSON-схем Stage 1.
- **Тестовая матрица:**
  - Протокольные тесты MCP-клиента (инспекция инструментов, выполнение вызовов, валидация возвращаемого форматированного Markdown-контекста).
- **Риски:** Избыточный объем сериализуемой геометрии в промпте LLM (необходимость сжатия структур `GeometryState` в контексте).

---

### Stage 5 — REST API Service (Удаленный сетевой сервис)
- **Цель:** Развертывание легковесного, безопасного HTTP-сервиса OMR для интеграции с удаленными облачными платформами.
- **Зависимости:** Stage 1, Stage 2.
- **Проектируемые файлы:**
  - `src/ail/server/app.ts` — Express / Node.js HTTP шлюз;
  - `src/ail/server/routes.ts` — маршруты `/api/v3/capabilities`, `/api/v3/operations/*`, `/api/v3/verify/*`;
  - `src/ail/server/middleware/auth.ts` — базовая аутентификация и rate-limiting.
- **Критерии готовности:**
  - Все эндпоинты возвращают канонические ответы согласно `OMR_PHASE_3_0_AGENT_PROTOCOL_SPECIFICATION.md`.
  - Время ответа сервиса (без учета сети) $< 5$ мс.
- **Тестовая матрица:**
  - HTTP интеграционные тесты (supertest): статус-коды 200, 400, 422, 429, 500.
  - Нагрузочные тесты на конкурентные запросы.
- **Риски:** Уязвимости сетевого периметра (необходимость строгой проверки входных пакетов на DoS).

---

### Stage 6 — External Tool Adapter (Мост к сторонним симуляторам оригами)
- **Цель:** Реализация адаптера для делегирования геометрических расчетов внешним программам (симуляторам оригами, CAD-системам) с обязательной последующей Zero-Trust проверкой в `L7`.
- **Зависимости:** Stage 2, завершение `Phase 2.4` (для корректной работы верификатора площадей).
- **Проектируемые файлы:**
  - `src/ail/external/ToolAdapter.ts` — абстрактный базовый класс адаптера внешних инструментов;
  - `src/ail/external/converters/foldFormat.ts` — двусторонний конвертер `GeometryState ↔ .FOLD JSON`;
  - `src/ail/external/drivers/cliProcessDriver.ts` — песочница для безопасного запуска CLI-утилит.
- **Критерии готовности:**
  - Ни один результат внешней программы не возвращается клиенту без явной отметки `UNTRUSTED_EXTERNAL_CLAIM` и прохождения `L7 verifyResult`.
- **Тестовая матрица:**
  - Негативные контроли: внешняя утилита возвращает искаженную геометрию $\to$ `L7` гарантированно возвращает `FAIL`, AIL возвращает `VIOLATED`.
- **Риски:** Зависание внешнего процесса (требуются жесткие таймауты `SIGKILL`).

---

### Stage 7 — Multi-Agent Workflows & Collaborative Verification
- **Цель:** Поддержка сложных распределенных сценариев, в которых несколько агентов с разными ролями (Planner, Reviewer, Verifier, Physics Simulator) координируют работу над одним оригами-проектом.
- **Зависимости:** Stage 2, Stage 4, Stage 5.
- **Проектируемые файлы:**
  - `src/ail/multiagent/SessionManager.ts` — управление версионированными рабочими пространствами;
  - `src/ail/multiagent/ProvenanceLedger.ts` — цепочка авторства и шагов агентов.
- **Критерии готовности:**
  - Доказана защита от сговора агентов: консенсус LLM не может отменить вердикт `L7 FAIL`.
- **Тестовая матрица:**
  - Симуляция сговора двух агентов, передающих некорректный шаг как истинный $\to$ сервис выносит статус `VIOLATED`.
- **Риски:** Конфликты версий `sourceState.version` при одновременной записи несколькими агентами (решается оптимистичной блокировкой `STATE_VERSION_MISMATCH`).
