# Reuse & Gap Analysis — Аудит готовых компонентов и пробелов

Анализ выполнен с опорой на переданные спецификации и фактическую инспекцию архива `Origami-Geometry-Core-main` (PCRS).

---

## 1. Что реально существует и подтверждено (в архиве `Origami-Geometry-Core`)

| Компонент / Путь в PCRS | Фактическое назначение | Ограничения | Статус переиспользования |
| :--- | :--- | :--- | :--- |
| `src/core/reflection.ts` | Чистое 2D-ядро плоских отражений (`R = 2uuᵀ - I`, `Float64`, без DOM) | Только 2D-жёсткие отражения; не включает топологию граней или 3D | **REUSE (после адаптации под L2)** |
| `src/verifier/independentVerifier.ts` | Автономный Zero-Trust верификатор (собственная формула Гаусса, коды ошибок `CAPABILITY_GAP`, `INVARIANT_VIOLATION_ISOMETRY`) | Допуски (`coord: 1e-7`, `area: 1e-9`) эмпирически проверены лишь для `L ≤ 2` | **REUSE + расширение в L7** |
| `src/construction/pointToPoint.ts` и `pointToPointVerifier.ts` | Построение сгиба «точка-к-точке» и его верификатор | Привязано к частной конструкции PCRS | **REUSE как эталонный тест** |
| `src/core/seq001Test.ts`–`seq003ErrorLocalization.ts` | Тесты последовательностей и локализации ошибок (вкл. negative controls) | Охватывают только 2D-цепочки отражений | **REUSE для регрессий Phase 2** |
| `ARCHITECTURE/REUSE_CANDIDATES.md` | Зафиксированные паттерны: `RC-02` (Zero-Trust импорт), `RC-03` (`CAPABILITY_GAP ≠ FALSE`), `RC-04` (трёхуровневая изоляция состояния) | Архитектурные решения, требующие переноса в контракты OMR | **ADOPT в архитектуру OMR** |

## 2. Кандидаты на переиспользование из других стендов (после аудита)

- **Из `Portable-Geometric-State-2D`:** контракт `Polygon(n)`, разделение границ и диагоналей, `portableId != localId`, `Construction DAG` → **целевая база для `Contract 01 (L1 ↔ L2)`**.
- **Из `AI Geometry Skill` и `Fedorov-Symmetry-Stand-V2`:** точная арифметика на `BigInt` (`GIEM v0.1`, рациональные матрицы `STL V1`) и шлюз `Gatekeeper` → **референс для устранения дрейфа `Float64` в `L7`**.
- **Из `SOL-Triad-Engine-v2`:** проверка допустимости переходов `Sᵢ → Sᵢ₊₁` → **шаблон для `Process Verification`**.
- **Из `Fe3uni-Harmonic-Analytics-v3.0`:** `SoftThresholdPenalty`, `1DStateMatcher` → **кандидат в `L6` (Phase 6)** при обязательном исключении вырожденной метрики `StructuralDensity`.
- **Из `3D-Geometry-Reasoning-Stand-v2`:** сферические конусы вершин (`LSM/LVG`) и монотонные переходы `t₁ > t₀` → **задел для Phase 5 (`L2/L4` 3D)**.

## 3. Выявленные пробелы и противоречия

| Пробел / Противоречие | Суть проблемы | Влияние на проект | Решение на Stage 1 / Phase 2 |
| :--- | :--- | :--- | :--- |
| **Разрыв `Float64` vs `BigInt`** | `PCRS` работает в `Float64` с эмпирическими допусками для `L ≤ 2`, тогда как `GIEM` и `STL V1` используют точную рациональную арифметику | Несогласованность допусков при масштабировании или многократных сгибах | Явно фиксировать домен применимости `L ≤ 2` в `Contract 02` и заложить интерфейс точного пересчёта |
| **Отсутствие формализованного L3** | В `PCRS` нет модели перекрытия слоёв (`Z-order`); 2D-отражение не задаёт порядок «выше/ниже» однозначно | Невозможно переходить к многослойным моделям (`Reverse`, `Squash`, `Pleat`) | Оставить L3 вне Phase 2; запланировать `L2 ↔ L3` в Phase 5 |
| **Непроверенные внешние API** | `Ori Studio` (Rust/WASM), `Oriedita` (Java), `OrigamiSimulator` (WebGL) не имеют готовых унифицированных RPC-интерфейсов в нашем контуре | Нельзя проектировать адаптеры «вслепую», предполагая несуществующий SDK | Ввести статус API (`Подтверждено / Требует инспекции`) в Tool Integration Architecture |
| **Отсутствие единого формата `TRACE`** | `PCRS`, `PGS-2D` и `vsam` используют разные структуры журналов и снимков состояний | Разрывается сквозная цепочка `Process Verification` | Унифицировать минимальный `TRACE` в `FIRST_PROTOTYPE_SPEC.md` |
| **Скрытие ошибок под `CAPABILITY_GAP`** | Риск помечать программный баг как «неподдерживаемую возможность» | Потеря надёжности `L7` | Ввести строгий реестр ограничений ядра и отдельные негативные тесты |
