# OMR — Epistemic Vector Specification (`OMR_EPISTEMIC_VECTOR_SPECIFICATION.md`)

**Версия:** Interface Contract Audit v1.0 (аналитическая спецификация; **не является утверждённым каноном**, программный код и `L1–L7` **не изменялись**).  
**Цель (Задача 1):** Проверить точное определение трёхосевого эпистемического вектора в `OMR_CROSS_ARCHITECTURE_AUDIT.md`, формализовать значения осей, допустимые комбинации, представление `UNKNOWN`, разграничение `NOT_VERIFIED / INFEASIBLE / INSUFFICIENT_CONTEXT` и правила независимого изменения осей.

**Обозначения статуса каждого определения:**
- `EXISTING` — уже определено в исходных документах (`src/core/types.ts`, `docs/ARCHITECTURE.md`, `PWRP_V1_1_*`, `MCAR_*`, `OMR_CROSS_ARCHITECTURE_AUDIT.md`);
- `DERIVED` — непосредственно следует из существующих правил;
- `PROPOSED` — новое предложение данного аудита для закрытия обнаруженных пробелов;
- `UNRESOLVED` — вопрос остаётся открытым до последующего решения владельца / фаз `Phase 3–8`.

## 1. Извлечение точного определения из `OMR_CROSS_ARCHITECTURE_AUDIT.md`

В `OMR_CROSS_ARCHITECTURE_AUDIT.md` (раздел 4, строки 54–68) приведено следующее определение (`EXISTING` в Audit v1.0; дублируется здесь в текстовой и LaTeX-форме во избежание проблем рендеринга):

- **Формула (`EXISTING` в Audit v1.0):**  
  `Verdict = (M_OMR, C_MCAR, P_PWRP-10)`  
  $$\text{Verdict} = \big(\;\mathbf{M}_{\text{OMR}},\;\mathbf{C}_{\text{MCAR}},\;\mathbf{P}_{\text{PWRP-10}}\;\big)$$
- **Смысл трёх осей (`EXISTING` в Audit v1.0):**
  1. **`M_OMR`** (`L7 Verifier`) — математическая корректность геометрических операций и контракта `OperationRequest ↔ Witness` в точности $\tau_{\text{geometry}}$.
  2. **`C_MCAR`** (`CRP-01 / MCAR`) — конструктивная определённость и происхождение объекта (`Single-Piece / Modular / Hybrid` и связность `COMPONENTS ↔ JOINTS` либо удержание `HYPOTHESIS_SET` с `UNKNOWN`).
  3. **`P_PWRP-10`** (`PWRP v1.1 + PWRP-10`) — физическая допустимость и степень её подтверждения при заданных материалах, швах, устойчивости и оснастке.

### Выявленные пробелы и расхождения при аудите извлечения
1. **`[GAP / UNRESOLVED]` Разночтение допустимых значений `M_OMR`:** в `src/core/types.ts` (`VerificationStatus`) определены только `'PASS' | 'FAIL' | 'UNDETERMINED'`, в `docs/ARCHITECTURE.md §3` запланирован `'CAPABILITY_GAP'`, в таблице §4 `OMR_CROSS_ARCHITECTURE_AUDIT.md` введён `'NOT_APPLICABLE'`, а в таблице §5 (строка 4) дополнительно появилось значение `'OBSERVED_ONLY'` без определения.
2. **`[GAP / PROPOSED]` Наследие `MATHEMATICALLY_VALID` внутри `PWRP-10`:** в `PWRP_V1_1_PATTERN_CATALOG.md` (строка 197) `MATHEMATICALLY_VALID` всё ещё числится среди 5 статусов `PWRP-10`, что при переходе к вектору `(M, C, P)` создаёт дублирование с осью `M_OMR`.
3. **`[GAP / PROPOSED]` Отсутствие матрицы допустимых комбинаций и правил независимого изменения осей:** в `OMR_CROSS_ARCHITECTURE_AUDIT.md` перечислены 4 запрета, но не задана полная таблица совместимости `(M, C, P)` и правила видимости гипотез при `UNKNOWN`.

## 2. Точный состав значений каждой оси и их статусы

### 2.1. Ось `M_OMR` — Математическая корректность (`L7` / формальная модель)
| Значение | Источник и смысл | Статус определения |
| :--- | :--- | :--- |
| `PASS` | Все проверенные переходы/операции удовлетворяют аксиомам и контракту `OperationRequest ↔ Witness` (`L7`). | `EXISTING` (`src/core/types.ts`) |
| `FAIL` | Нарушены математические инварианты, аксиомы операции или привязка `requestBound` / `witnessBound`. | `EXISTING` (`src/core/types.ts`) |
| `UNDETERMINED` | Нечисловые/вырожденные входные данные (`NaN`, `Infinity`, нулевая нормаль и т.п.) либо формализация не завершена. | `EXISTING` (`src/core/types.ts`) |
| `CAPABILITY_GAP` | Операция не поддерживается текущей реализацией ядра (запланировано в `docs/ARCHITECTURE.md §3`). | `EXISTING` *(planned in `docs/ARCHITECTURE.md`)* |
| `NOT_APPLICABLE` | Геометрия объекта не сведена к поддерживаемым математическим примитивам (напр., внешний 3D-узел без 2D-отражения). | `EXISTING` *(в Audit v1.0 §4)* / `PROPOSED` *(для контракта AI Skill)* |
| `OBSERVED_ONLY` | Упомянуто в Audit v1.0 §5 как «наблюдаемая `GLOBAL_GEOMETRY` без трассы `L2`». Не определено формально относительно `UNDETERMINED` / `NOT_APPLICABLE`. | `UNRESOLVED` *(требуется либо свести к `UNDETERMINED`, либо выделить явно)* |

### 2.2. Ось `C_MCAR` — Конструктивное происхождение и композиция (`CRP-01 / MCAR`)
| Значение | Источник и смысл | Статус определения |
| :--- | :--- | :--- |
| `VERIFIED_SINGLE_PIECE` | Подтверждено происхождение из одного исходного листа/заготовки (альтернативы отклонены). | `EXISTING` *(в Audit v1.0 §4)* |
| `VERIFIED_MODULAR` | Подтверждена сборка из независимо изготовленных модулей с определёнными `COMPONENTS` и `JOINTS`. | `EXISTING` *(в Audit v1.0 §4)* |
| `VERIFIED_HYBRID` | Подтверждено комбинирование сложенных элементов и дополнительных деталей/крепежей. | `EXISTING` *(в Audit v1.0 §4)* |
| `AMBIGUOUS_HYPOTHESES` | По форме/признакам в `HYPOTHESIS_SET` активны $\ge 2$ конкурирующих гипотез происхождения (ни одна не доказана как единственная). | `EXISTING` *(в Audit v1.0 §4)* |
| `PROVENANCE_UNKNOWN` | Происхождение и/или состав компонентов не указаны и не восстановлены из наблюдений (`COMPONENT_PROVENANCE = UNKNOWN`). | `EXISTING` *(в Audit v1.0 §4)* |
| `CONSTRUCTIVELY_INFEASIBLE` | Ни одна гипотеза композиции `COMPONENTS ↔ JOINTS → WHOLE` не способна образовать требуемое целое (топологическая несобираемость). | `EXISTING` *(в Audit v1.0 §4)* |
| `VERIFIED_MULTI_PART_ENCLOSURE` | Появление в `MCAR` категории `D` (`Multi-Part Enclosure`) требует решения: кодировать её отдельным значением `C_MCAR` или подтипом внутри `VERIFIED_MODULAR` / `VERIFIED_HYBRID`. | `UNRESOLVED` |

### 2.3. Ось `P_PWRP-10` — Физическая допустимость и полнота проверки (`PWRP v1.1 + PWRP-10`)
| Значение | Источник и смысл | Статус определения |
| :--- | :--- | :--- |
| `PHYSICALLY_FEASIBLE` | Активированные физические закономерности (`PWRP-01..09, 11..14`) проверены при полных данных без нарушений. | `EXISTING` (`PWRP v1.1`) |
| `PHYSICALLY_INFEASIBLE` | Доказано нарушение хотя бы одного физического закона/ограничения (разрыв материала, коллизия объёмов, опрокидывание, *buckling*, недоступность замыкающего шва). | `EXISTING` (`PWRP v1.1`) |
| `PHYSICALLY_NOT_VERIFIED` | Исходный контекст в основном известен, но необходимая физическая проверка не выполнена (нет решателя/расчёта или испытательной модели). | `EXISTING` (`PWRP v1.1`) |
| `INSUFFICIENT_PHYSICAL_CONTEXT` | Отсутствуют критические входные физические или конструктивные параметры (материал, толщина, `JOINING_METHOD`, время/нагрузка), без которых физический вывод невозможен. | `EXISTING` (`PWRP v1.1`) |
| `CONDITIONAL_PER_HYPOTHESIS` | При неоднозначности `C_MCAR` физическая допустимость оценена **условно отдельно для каждой ветки** `HYPOTHESIS_SET`, без слияния в единый вердикт. | `EXISTING` *(в Audit v1.0 §4)* / `PROPOSED` *(расширение относительно `PWRP v1.1`)* |
| *(Устаревшая проекция)* `MATHEMATICALLY_VALID` | В `PWRP v1.1` входило в перечень `PWRP-10`. В трёхосевом векторе **должно выводиться из `M_OMR = PASS`**, а не занимать слот оси `P`. | `DERIVED` / `PROPOSED` *(уточнение стыка)* |

## 3. Допустимые и запрещённые комбинации `(M_OMR, C_MCAR, P_PWRP-10)`

Ниже приведены правила совместимости (`DERIVED` из инвариантов Audit v1.0 §4 + `PROPOSED` для полноты контракта):

| Комбинация `(M, C, P)` | Допустимость | Смысл и обоснование | Статус правила |
| :--- | :--- | :--- | :--- |
| `(PASS, VERIFIED_*, PHYSICALLY_FEASIBLE)` | **ДОПУСТИМА** | Целевое полное подтверждение: математика верна, происхождение известно, физические проверки пройдены. | `DERIVED` |
| `(PASS, VERIFIED_*, PHYSICALLY_NOT_VERIFIED)` | **ДОПУСТИМА** | Геометрия доказана в `L7`, способ изготовления задан, но физическая проверка (напр. 3D-устойчивость) не проводилась. | `EXISTING` (Audit §4) |
| `(PASS, VERIFIED_*, INSUFFICIENT_PHYSICAL_CONTEXT)` | **ДОПУСТИМА** | Геометрия верна в `L7`, происхождение известно (напр. `Single-Piece`), но не задан материал/толщина. | `DERIVED` |
| `(PASS, VERIFIED_*, PHYSICALLY_INFEASIBLE)` | **ДОПУСТИМА** | Идеальная 2D/3D геометрия сходится математически, но физически невыполнима (бумага рвётся или клапан сминается). | `EXISTING` (`PWRP-10`) |
| `(PASS, AMBIGUOUS_HYPOTHESES / PROVENANCE_UNKNOWN, CONDITIONAL_PER_HYPOTHESIS / INSUFFICIENT_PHYSICAL_CONTEXT)` | **ДОПУСТИМА** | Геометрическая модель (напр. отдельных граней/модуля) корректна, но происхождение не подтверждено — физика даётся только условно по гипотезам. | `PROPOSED` |
| `(FAIL, *, PHYSICALLY_FEASIBLE)` *(для одной и той же операции)* | **ЗАПРЕЩЕНА** | Нельзя объявлять физически осуществимой реализацию математически ложной/разорванной геометрической трассы без её перепостроения (`M` должно быть пересчитано или отсечено). | `PROPOSED` |
| `(*, PROVENANCE_UNKNOWN / AMBIGUOUS_HYPOTHESES, PHYSICALLY_FEASIBLE)` *(безусловно)* | **ЗАПРЕЩЕНА** | Пока происхождение (и зависящие от него швы `JOINING_METHOD`) не установлено, безусловное утверждение `PHYSICALLY_FEASIBLE` запрещено: разные гипотезы имеют разные физические отказы (`S15`, `M4`). | `DERIVED` |
| `(*, PROVENANCE_UNKNOWN, VERIFIED_MODULAR)` *(коллапс внутри `C`)* | **ЗАПРЕЩЕНА** | Запрет подмены неизвестного происхождения доказанной модульностью (§6 Audit). | `EXISTING` |
| `(PASS, CONSTRUCTIVELY_INFEASIBLE, PHYSICALLY_FEASIBLE)` | **ЗАПРЕЩЕНА** | Если компоненты не могут конструктивно образовать целое (`CONSTRUCTIVELY_INFEASIBLE`), физическая осуществимость сборки невозможна (допустимо только `PHYSICALLY_INFEASIBLE` или `NOT_VERIFIED`). | `DERIVED` |
| `(*, *, PHYSICALLY_INFEASIBLE)` при отсутствии доказанного нарушения закона/ограничения *(только из-за нехватки данных)* | **ЗАПРЕЩЕНА** | Запрет превращения отсутствия проверки/данных в физическую невозможность (§6 Audit). | `EXISTING` |

> **Примечание о `CONDITIONAL_PER_HYPOTHESIS` (`PROPOSED`):** когда `C_MCAR ∈ {AMBIGUOUS_HYPOTHESES, PROVENANCE_UNKNOWN}`, вектор уровня объекта дополняется **картой веток** `BranchVerdicts: Map<branchId, (M_branch, C_hypothesis, P_branch)>`, чтобы агент мог честно показать: «при гипотезе 1 (1 лист) $\to$ `PHYSICALLY_INFEASIBLE` по `PWRP-01`; при гипотезе 2 (модули Sonobe) $\to$ `INSUFFICIENT_PHYSICAL_CONTEXT` (нужны параметры карманов)».

## 4. Представление `UNKNOWN` на двух уровнях

Для предотвращения смешения неизвестных фактов с опровергнутыми или подтверждёнными значениями различаются **два уровня представления `UNKNOWN`**:

1. **Уровень атрибута / поля (`Attribute-Level UNKNOWN` — `EXISTING` в `MCAR`):**
   - Используется внутри структур `MCAR` (`COMPONENT_PROVENANCE = UNKNOWN`, `JOINING_METHOD = UNKNOWN`, `LOCAL_GEOMETRY = UNKNOWN`, `ASSEMBLY_SEQUENCE = UNKNOWN`, `JOINT_REVERSIBILITY = UNKNOWN`, `INTERFACE_DOF = UNKNOWN`) и физических паспортов (`MATERIAL = UNKNOWN`, `THICKNESS = UNKNOWN`).
   - **Семантика:** *значение существует в реальном объекте, но не наблюдаемо и не сообщено агенту*. Не равно `null`/`false`/`[]`.
2. **Уровень вектора решений (`Vector-Level UNKNOWN Representation` — `DERIVED` + `PROPOSED`):**
   - В оси `M_OMR` $\to$ `UNDETERMINED` (или `NOT_APPLICABLE` / `OBSERVED_ONLY`, статус уточнения `UNRESOLVED`);
   - В оси `C_MCAR` $\to$ `PROVENANCE_UNKNOWN` (если неизвестен даже состав гипотез) или `AMBIGUOUS_HYPOTHESES` (если выделено множество кандидатов в `HYPOTHESIS_SET`);
   - В оси `P_PWRP-10` $\to$ `INSUFFICIENT_PHYSICAL_CONTEXT` (если не хватает данных) или `CONDITIONAL_PER_HYPOTHESIS` (если условная оценка зависит от неизвестной конструктивной ветки).

## 5. Строгое разграничение `NOT_VERIFIED`, `INFEASIBLE` и `INSUFFICIENT_CONTEXT`

| Статус оси `P_PWRP-10` | Статус | Что отсутствует или нарушено | Что требуется от агента |
| :--- | :--- | :--- | :--- |
| **`PHYSICALLY_NOT_VERIFIED`** | `EXISTING` (`PWRP-10`) | Входные данные могут быть заданы (или известна сама задача), но **не выполнена физическая проверка/модель** (нет решателя, нет $S$-$N$ кривой или испытаний прототипа). | Честно указать список активированных, но не проверенных паттернов `PWRP` и не выдавать гарантию осуществимости. |
| **`INSUFFICIENT_PHYSICAL_CONTEXT`** | `EXISTING` (`PWRP-10`) | Невозможно даже приступить к проверке из-за **отсутствия обязательных входных фактов** (`MATERIAL`, `THICKNESS`, `JOINING_METHOD = UNKNOWN`, `COMPONENT_PROVENANCE = UNKNOWN`). | Остановить угадывание и сформировать точный запрос недостающих параметров. |
| **`PHYSICALLY_INFEASIBLE`** | `EXISTING` (`PWRP-10`) | **Доказано нарушение** хотя бы одного физического закона или ограничения при известных условиях (интерференция объёмов, разрушение материала, отсутствие равновесия, *buckling*, невозможный доступ при закрытии шва). | Предъявить конкретный `PWRP-XX` и физическую причину отказа; при возможности и разрешении инициировать возврат к пересмотру конструктивной гипотезы. |

## 6. Независимость изменения осей `(M_OMR, C_MCAR, P_PWRP-10)`

Может ли изменение одной оси происходить без изменения остальных? **Да — но строго асимметрично (`DERIVED` + `PROPOSED`):**

1. **Изменение `P_PWRP-10` БЕЗ изменения `M_OMR` и `C_MCAR` (ДА):**
   - Пользователь уточнил материал (бумага 80 г/м² $\to$ хрупкий картон 400 г/м²): геометрические трассы `L2/L7` (`M_OMR = PASS`) и однолистовое происхождение (`C_MCAR = VERIFIED_SINGLE_PIECE`) остаются **без изменений**, меняется только `P_PWRP-10` (`INSUFFICIENT_PHYSICAL_CONTEXT` $\to$ `PHYSICALLY_INFEASIBLE`).
2. **Изменение `M_OMR` БЕЗ изменения `C_MCAR` (ДА, при провале шага) / С влиянием на `P` (УСЛОВНО):**
   - Исправление численной/геометрической ошибки внутри одного сгиба (изменение `M_OMR: FAIL → PASS`) не меняет `C_MCAR = VERIFIED_SINGLE_PIECE`. При этом если `P` было `PHYSICALLY_NOT_VERIFIED` или `INSUFFICIENT_PHYSICAL_CONTEXT`, оно остаётся неизменным; но если `P` было `PHYSICALLY_FEASIBLE`, оно должно быть перепроверено для исправленной геометрии (сброс в `PHYSICALLY_NOT_VERIFIED` до повторной проверки).
3. **Изменение `C_MCAR` БЕЗ аннулирования уже доказанных локальных `M_OMR` (ДА, ключевое правило Задачи 4):**
   - При пересмотре конструктивной гипотезы (например, `Single-Piece → Modular` или смена `JOINING_METHOD` с клея на внешний замок) меняется `C_MCAR` и заново запускается `P_PWRP-10` для новых швов, но **уже доказанные `L7 PASS` на неизменённых индивидуальных компонентах/операциях сохраняются** (`M_per_component = PASS`), пока их собственный `OperationRequest` и `sourceState` не менялись.
   - Меняется только `M_assembly` (математическая модель композиции новой сборки), если изменилась топология сопряжений.

## 7. Сводка открытых эпистемических вопросов (`UNRESOLVED`)

1. **`EV-U01` (`OBSERVED_ONLY` vs `UNDETERMINED` / `NOT_APPLICABLE`):** необходимо выбрать единое каноническое имя в `M_OMR` для ситуации «3D-форма объекта наблюдается, но не представлена последовательностью операций `L2`».
2. **`EV-U02` (`VERIFIED_MULTI_PART_ENCLOSURE`):** определить, является ли `Multi-Part Enclosure` самостоятельным значением оси `C_MCAR` или структурным тегом поверх `VERIFIED_MODULAR` / `VERIFIED_HYBRID`.
3. **`EV-U03` (Упразднение `MATHEMATICALLY_VALID` из перечня `PWRP-10`):** при следующей ревизии документов `PWRP` необходимо решить, убирается ли `MATHEMATICALLY_VALID` из `PWRP-10` полностью (т.к. её полностью замещает ось `M_OMR`).
